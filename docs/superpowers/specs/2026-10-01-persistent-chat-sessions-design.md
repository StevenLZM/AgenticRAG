# 持久化多轮聊天与会话管理设计

日期：2026-10-01。

状态：需求、总体方案与本文书面设计均已获用户确认；现已实现并完成集成与浏览器验收，最终独立审查进行中。用户指定本次优化直接在 `main` 分支开发。

源码核对基线：`main / b989c96`。本文是确认的行为契约；实际验证范围见 [验收记录](../../validation/2026-10-01-persistent-chat-sessions.md)。现有控制台设计中的三栏调试布局和日志展示要求，由本文的聊天交互要求替代；用户隔离、公开答案投影和证据审计边界继续适用。

## 1. 已确认的需求

用户希望把分离的提问框、回答区改成类似 GPT 的连续聊天体验。已经确认：

1. 支持完整历史会话：新建、列表、切换、刷新恢复和打开旧会话继续追问。
2. 用户问题与系统回答在同一可滚动区域按时间排列，输入框固定在底部。
3. 同一用户的各会话共用知识库；Mem0 长期记忆继续按 `user_id` 隔离，不按会话重新建命名空间。
4. 不在聊天页展示检索日志。执行中仅显示简短阶段，最终结果完成后一次性展示正文。
5. 每条回答的来源按需展开，展示该轮对应的文档片段。
6. 用户向上翻阅时不强制滚到底部；提供“回到最新”。
7. 支持停止当前任务；同一会话当前任务结束后再发送下一条。
8. 切换会话不取消后台任务，返回会话后恢复当前状态。
9. 文档上传、Mem0 管理保留在按需打开的工具入口中。
10. 首版包含会话重命名和删除。删除会话不删除文档或长期记忆。

成功标准是：用户可以持续问答、回看、刷新和切换会话，不丢失已受理的问答，不出现跨会话回答、来源错配或重复提交产生的额外 Run。

## 2. 方案选择与范围

采用原生 HTML/CSS/JavaScript 和 FastAPI 同源页面，复用现有 Query Run 作为一轮问答的事实来源，增加会话元数据与历史接口。

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 会话元数据 + 现有 Run 问答投影 | 沿用持久化任务、取消、审计答案和用户范围；问答内容只有一个存储真相 | 需要新增会话索引、历史查询和来源快照；本次采用 |
| 独立消息存储 + Run 同步 | 适合编辑消息、分支对话、多版本回答 | 需要处理消息与 Run 的双写、排序和恢复；本轮没有这些需求 |

不将现有 `messages` 表启用为第二份聊天记录。每个已受理 Run 投影出一条用户消息和一条系统消息；正在执行时，系统消息是状态占位，结束后原位替换为最终结果。

本轮不包含消息编辑、重新生成、分支对话、会话搜索、逐 token 输出、LLM 会话摘要、会话绑定文档、身份认证/RBAC、MQ 替换或多 Worker。会话完整保存与模型完整读取所有历史是两个契约：界面保存全部已受理轮次，模型继续使用现有有界历史策略。

旧控制台产生的散落 Run 不自动导入会话列表，也不按问题相似度合并。它们保留原记录和原有 API 访问方式。新界面的历史列表从本功能创建的会话开始，避免把历史评测、脚本和调试 Run 混入用户聊天。

## 3. 页面交互

### 3.1 布局

- 左侧：新建对话、按最近活动排序的会话列表、会话菜单，以及“文档”“记忆”“系统状态”工具入口。
- 主区域顶部：当前会话标题与菜单。
- 主区域中部：连续消息列表。用户与系统消息视觉区分；问题不会留在输入框中代替聊天记录。
- 主区域底部：随内容增高的输入框、发送/停止按钮。
- 来源在对应回答下展开，不使用会被下一轮覆盖的全局证据面板。
- 窄屏将会话列表与工具收进抽屉；关闭后回到聊天，不压缩出三个横向窄栏。

正文沿用公开答案的 segment 顺序，保留段落、标题、换行和列表文本。用户文本、回答、会话标题和证据均作为不可信文本渲染，首版不支持原始 HTML，也不引入新的前端构建框架。

### 3.2 新建、标题与管理

- 点击“新建对话”即在服务端创建空会话，初始标题为“新对话”；成功前禁用重复点击。
- 第一条问题成功受理时，以去除首尾空白、将连续空白折叠后的前 30 个 Unicode 字符设置默认标题；超长加省略号。这里的“摘要”是确定性截取，不调用模型。
- 用户可重命名为 1–100 字符的非空标题。手动命名后不再被首问或回答覆盖。
- 最近活动时间在受理新问题、Run 首次进入终态时更新；查看、展开来源、重命名不改变会话排序。
- 删除先弹出简短确认。存在 `queued/running/cancel_requested` Run 时拒绝删除并提示先停止或等待；不因删除动作偷偷取消任务。
- 删除为逻辑删除：会话从列表移除，公开会话和关联 Run 接口拒绝访问；后台审计记录、checkpoint 不物理清除。删除确认说明“不影响知识库和长期记忆”。完整数据擦除不属于本轮。

### 3.3 输入与消息

- Enter 发送，Shift+Enter 换行；中文输入法 composition 期间的 Enter 只确认输入，不发送。
- 输入继续限制为 32,000 字符；空白问题不提交。
- 点击发送立即显示本地“提交中”问题和系统占位。服务端确认受理后绑定 Run ID，并清空输入框。
- 提交明确失败时保留草稿和错误提示；结果未知时保留待确认状态，不换新请求 ID 自动重发。
- 会话已有活动 Run 时，输入框允许编辑下一条草稿，但发送禁用；只提交停止请求后仍须等待实际终态。
- 失败、取消、拒答、澄清和研究预算耗尽都保留为该轮系统消息，不删掉问题，不显示未经审核的草稿。
- 会话草稿仅存在当前页面内存，切换时按会话保留；刷新恢复承诺覆盖服务端已受理的轮次，不承诺恢复尚未提交的草稿。

### 3.4 滚动与长历史

- 初次进入会话加载最新 30 轮，展示顺序从旧到新，并定位至最新消息。
- 向上加载更早记录，采用游标分页；插入历史时保持原可见消息的视觉位置。
- 距离底部 80px 内视为跟随最新。状态更新或最终回答到达时，仅在跟随模式下滚动到底部。
- 用户向上翻阅后显示“回到最新”，消息更新不抢滚动位置。
- 状态更新使用同一消息节点，不逐事件追加消息。展开来源不强制滚动到页面底部。
- 输入、会话菜单、来源展开和抽屉支持键盘操作；加载状态使用简短的 `aria-live` 通知。

## 4. 身份、存储与一致性

### 4.1 身份关系

`user_id -> chat_session -> thread_id -> 多个 Run`。

- `user_id` 继续由服务端 `UserScope` 注入；客户端不传用户身份，也不能从 session ID 获得权限。
- 新 session ID 使用服务端生成的 UUIDv7；其 `thread_id` 固定等于该 ID，创建后不可更换。
- 每次追问创建新 Run，始终携带这个 `thread_id`；不能为每条消息生成新 thread。
- 知识库过滤和 Mem0 namespace 继续只由当前用户范围决定，不附加 session ID。
- 所有会话读写、分页、提交查证、取消和来源读取都验证用户归属与未删除状态。

### 4.2 数据模型

新增 `chat_sessions` 表：

| 字段 | 契约 |
| --- | --- |
| `id` | UUIDv7 主键，同时作为本功能的 thread ID |
| `user_id` | 服务端用户范围，非空 |
| `creation_request_id` | 客户端为一次新建操作生成的 UUID；只用于去重 |
| `title` | 1–100 字符，默认“新对话” |
| `title_source` | `default / first_question / manual` |
| `created_at`、`updated_at` | UTC 时间，微秒精度 |
| `last_activity_at` | UTC 时间，列表排序依据 |
| `deleted_at` | 可空，逻辑删除标记 |

唯一约束 `(user_id, creation_request_id)`；列表索引覆盖用户、删除状态、最近活动时间和 ID。

对 `agent_runs` 增量添加：

- `client_request_id`：可空 UUID，用于聊天提交去重，旧调用方可以不传。
- 唯一约束 `(user_id, thread_id, client_request_id)`；旧记录为 NULL，不改变原行为。
- `answer_sources`：可空、版本化 JSON，保存本轮最终回答的受控来源快照，结构见第 7 节。

不把来源片段塞入 `PublicAnswer`，不改变评测读取公开答案的现有字段口径。迁移不回填旧 Run，不改写历史快照、答案或 checkpoint。

### 4.3 提交事务与去重

聊天提交必须在一个短 MySQL 事务中完成：

1. 按当前用户读取并锁定 session，拒绝不存在或已删除会话。
2. 查找相同 `client_request_id`。若已存在且规范化后的问题相同，返回原 Run；问题不同返回 `409 IDEMPOTENCY_CONFLICT`。问题规范化仅去除首尾空白，不折叠内部空白或换行；保存和比较使用同一规范化值。
3. 验证同 session 没有活动 Run；现有 active-slot 唯一约束作为最终竞争保护。
4. 创建 Run 与 Outbox，设置首问标题并更新会话活动时间，然后提交。

去重查找优先于“已有活动 Run”判断。因此重复发送同一请求能获取原 Run，而非被自己的活动任务阻挡；终态后重复发送同一请求仍复用原 Run，不额外调用模型。

会话删除与发问使用同一 session 行锁：先完成删除则后来的发问被拒绝；先受理发问则删除被活动任务阻挡。

Worker 的租约校验、结果写入、来源快照写入，以及关联会话的终态活动时间更新，在同一次 `finish` 事务中提交。涉及 session 和 Run 的事务统一先锁 session、再处理 Run，避免与提交/删除的锁序相反。旧非聊天 Run 不需要 session 记录。

## 5. HTTP 契约

新增会话 API，沿用现有错误信封。请求模型拒绝额外字段。

| 方法与路径 | 行为 |
| --- | --- |
| `POST /v1/chat-sessions` | 请求包含 `creation_request_id`；首次返回 201，重复返回同一 session 的 200；已删除的相同创建请求返回 410，不复活会话 |
| `GET /v1/chat-sessions` | 游标分页，默认 30、最大 100；返回摘要和活动 Run ID/状态，不返回问答全文 |
| `GET /v1/chat-sessions/{session_id}` | 会话元数据、活动 Run 和最新状态；用于刷新恢复 |
| `PATCH /v1/chat-sessions/{session_id}` | 只允许更新 `title` |
| `DELETE /v1/chat-sessions/{session_id}` | 无活动 Run 时逻辑删除，返回 204；活动任务冲突返回 409；同用户重复删除可返回 204 |
| `GET /v1/chat-sessions/{session_id}/turns` | 默认 30、最大 100；以 `(created_at, run_id)` 游标向更早历史翻页，页内按时间升序返回 |
| `POST /v1/chat-sessions/{session_id}/turns` | `{query, client_request_id}`；新受理返回 202 与 Run，去重命中返回 200 与原 Run；不接受 evaluation 参数 |
| `GET /v1/chat-sessions/{session_id}/submissions/{client_request_id}` | 只读查询一次提交是否已受理，返回原 Run；尚无记录返回 404 |
| `GET /v1/chat-sessions/{session_id}/turns/{run_id}/sources` | 返回该轮的受控来源片段；验证 Run 确实属于会话 |

停止、Run 状态与事件流继续复用 `/v1/query-runs/{run_id}/cancel`、`GET /v1/query-runs/{run_id}` 和 `/events`。这些入口统一补充已删除聊天会话的访问检查，避免删除后仍通过旧 URL 读取或续接。

每轮响应包含 `run_id`、创建时间、问题、任务状态、公开答案、安全阶段、来源是否可展开，以及通用终态展示码。系统正文仍从 `project_public_answer` 获得，禁止返回 raw answer、prompt、tool payload 或隐藏推理。

会话列表按 `(last_activity_at DESC, id DESC)` 分页，前端按 ID 去重。活动时间会变化，因此列表分页不是冻结快照；重新聚焦页面或受理/完成当前任务时刷新首屏。轮次历史按不可变的创建时间和 ID 分页，不受回答完成顺序影响。

不存在、其他用户拥有和已删除的会话，对读取/发问统一返回 404。其他标签页已有活动任务时，返回 `409 SESSION_BUSY`，仅携带当前用户可见的活动 Run ID；前端附着到该 Run，同时保留本次尚未受理的草稿，不把两次不同的问题合并。`IDEMPOTENCY_CONFLICT` 则提示请求冲突，不自动附着或重新提交。

## 6. 执行阶段与恢复

### 6.1 简短阶段

新增固定事件 `QUERY_PHASE_CHANGED`，只公开 `run_id` 和受限 `phase` 枚举，复用现有持久化事件/SSE。阶段不从日志文本推断。

| 情况 | 用户看到的状态 |
| --- | --- |
| 本地提交尚未确认 | 提交中 |
| Run 已受理、queued | 等待中 |
| 路由、普通 Chat、生成或没有可确定细分阶段 | 处理中 |
| Fast RAG 开始检索 | 检索中 |
| 进入 Research 动作循环 | 研究中 |
| 实际进入证据充分性或答案忠实度/引用审核 | 审核中 |
| cancel_requested | 正在停止 |
| completed/failed/cancelled | 替换为最终回答或对应简短说明 |

研究内的子检索保持“研究中”，避免反复闪动；升级研究、重新生成和修订允许改变阶段。阶段由实际执行节点发出，不用计时器模拟进展。

当前 `generate_with_mandatory_audits` 内执行了真实生成与审核，后面的 faithfulness/citation Graph 节点主要记录结果；实施时必须在实际审核调用之前发送阶段，而不是等审核结束才显示“审核中”。

事件是辅助信息。阶段事件丢失时显示“处理中”，不阻断执行；Run 的持久化终态优先于任何晚到阶段事件。`ANSWER_FINALIZED` 事件本身不是发布依据，页面必须等到 Run 已提交终态并读取公开答案后才展示正文。

聊天区域不显示 event name、Run ID、模型重试次数或原始错误日志。可展示“暂时无法完成，请稍后重试”等安全说明；查询和来源中的实际文本继续按公开投影限制。

### 6.2 前端状态与连接

前端用 `session_id -> run_id -> turn` 的状态结构管理聊天，不再使用单一全局 answer 容器。每个 Run 保留自己的终态标记与 SSE cursor。

- 切换 session 时终止旧页面订阅和过期 GET，不发送取消 Run 请求。
- 所有异步回调检查 session ID、run ID 和视图代次；旧请求即使晚返回，也不能写入当前会话。
- 当前可见会话有活动 Run 时订阅事件；进入会话先 GET 当前 Run，再接续 SSE。
- SSE 断线按有界退避重连，三次失败后以 2 秒间隔轮询 Run；隐藏标签页暂停轮询，重新可见时立即核验。网络故障不伪装成任务失败。
- SSE 正常关闭后再 GET Run，只有读到终态才解除发送禁用；关闭连接不等于任务完成。
- 停止请求之后继续观察 Run，直至 cancelled 或其他实际终态。若任务在取消前已完成，展示最终结果。
- 后台会话不维持全部 SSE 连接；会话列表刷新时更新其活动标记，返回后恢复，不丢后台结果。

### 6.3 刷新与未知提交

在当前浏览器会话的 `sessionStorage` 中只保存选中的 session ID、待确认的创建/提交请求 ID 和必要的 Run/SSE 游标。聊天内容、来源、Mem0 文本和凭证不存入 LocalStorage 或 sessionStorage。

刷新时从服务端核验 session 所有权并加载历史；缓存只决定尝试打开哪个会话，不授予访问权限。

创建会话响应丢失时，携带原 `creation_request_id` 重试同一创建操作。发问响应丢失时，原页面可用同一问题和 `client_request_id` 重试；刷新后优先使用 submissions 查询和历史核验，不自动创建新 Run。暂未查到记录只表示“尚未确认受理”，不能当作肯定未执行而换新 ID 重发。用户可继续检查状态；未受理且刷新后丢失的草稿不伪造为服务端记录。

### 6.4 多轮语义与恢复的边界

继续使用 `SqlAlchemyConversationReader` 按同 `user_id/thread_id` 读取当前 Run 之前的已完成公开问答。当前策略最多保留 6 条角色消息、总计 8000 字符；这不是 6 个完整问答轮次。失败和仍在执行的 Run 不加入模型历史。

前端不自行拼接全部聊天记录到 query，不从其他 session 借历史，不将长期记忆 namespace 改为 thread ID。超出模型历史窗口的指代不保证自动找回；当前轮无法确定对象时沿用澄清路径。

本次的“刷新恢复”是恢复页面、已有任务和结果的观察，不创建第二个 Run。此前阅读已隔离复现 Query Worker 用初始状态重入而重置研究计数的进程级恢复缺口；本轮不声称修复它，也不扩展为 Worker 崩溃恢复改造。部署时必须排空活动任务；真实 Worker 崩溃接管属于独立可靠性验收项。

## 7. 每轮来源的可信展示

### 7.1 来源快照

当前公开答案包含 evidence ID 和 Parent ID，但不具备完整可展开片段。不能从最新会话 checkpoint 读取旧轮次来源，也不能只按 Parent ID 拼接当前任意文档内容。

新增版本化的内部 `AnswerSources` 投影，由实际通过审核的回答与当轮 `PackedEvidence` 构建：

- 只选择最终回答 segment 真正引用的 evidence ID，不把本轮所有检索候选都称为引用。
- 每条保存 evidence ID、document/version/parent ID、标题路径、可验证的页码范围、当轮实际进入上下文的证据片段，以及截断标记。
- 每条片段上限 2000 个 Unicode 字符，按最终回答中首次引用顺序去重并保留最多 64 条来源；其余计入 `omitted_source_count`，界面明确说明还有未展示的来源。
- 标题路径等文本元数据也必须有界，全部快照的 UTF-8 JSON 编码上限为 256 KiB。先预留所保留条目的受控元数据，再依次分配片段预算；因预算截短或省略的片段明确标记 `truncated` 或 `excerpt_omitted`，不突破条数/字节上限，也不伪装为完整展示。
- 引用条目必须与当轮 manifest 一致，授权检查不能由客户端或历史缓存代替。
- `run_id`、`runtime_config_snapshot_id` 写入快照；答案与来源在 Worker 受租约保护的同一终态更新中落盘。
- 纯 Chat、无正文终态和审核失败不生成知识库来源。来源投影校验异常时只标记 unavailable，不展示未经验证内容，也不以新模型请求补造来源。

来源缺失不允许绕过原答案审核；可用的、已审核答案可以展示，同时说明来源详情暂不可用。来源只是对已通过答案的附加呈现，不是另一次生成。

### 7.2 展开读取

来源接口先验证会话、Run 和用户归属，再核验每个文档的当前用户归属及未删除状态。文档文件名从这个受控文档查询获得，不暴露本机路径或内部 artifact URI。

- 文档仍可访问、版本未变：展示保存的原始片段和来源标识。
- 文档已更新：仍显示该回答使用的版本化历史片段，并标注“回答使用的是历史版本”；不能换成最新版本文本。
- 文档已删除或无法验证访问权：隐藏保存的片段，显示“来源已不可用”。已发布回答正文不因展开失败被替换。
- 来源快照不存在、格式损坏或超限：显示受控的 unavailable 状态，不退回到原始 checkpoint/tool payload。
- 前端不持久缓存来源正文。每次重新展开请求服务端，响应使用 `Cache-Control: no-store`；已展开来源在切换会话、工具操作后刷新或页面重新聚焦时重新核验。

默认只展示文档名、章节/页码和片段。审计与溯源元数据可以在来源区域内二次展开，只呈现该 Run 的公开安全字段；不恢复检索日志面板。

## 8. 兼容、部署与文件职责

保留旧 `/v1/query`、`/v1/query-runs` 的基本请求/响应语义，现有评测和脚本无需改用会话 API。新字段均为可选或可空；旧客户端不提供去重 ID 时保持现状。

旧入口若明确使用了已注册聊天 session 的 thread ID，必须经过同样的归属、未删除和活动任务检查，并在创建事务内维护该会话活动时间。已删除会话不能通过旧接口复活；其他用户不能通过猜测 thread ID 写入该会话。聊天 session 禁止承载 evaluation 请求，原评测 thread 继续隔离。

| 位置 | 职责 |
| --- | --- |
| `api/chat_sessions.py`（新增） | 会话、轮次、提交查证、来源 HTTP 投影 |
| `runtime/chat_sessions.py`（新增） | 会话创建/命名/删除和幂等发问服务，复用 Run 创建契约 |
| `persistence/chat_sessions.py`（新增） | scoped session 查询、分页、行锁、请求查证 |
| `persistence/repositories.py`、Alembic 新迁移 | 表结构、Run 可选字段、同事务创建和终态提交 |
| `query/answer_sources.py`（新增） | 有界来源快照契约与确定性投影 |
| `query/graph.py`、`query/audit.py`、事件白名单 | 实际阶段发出；不改变审核规则、路由和预算 |
| `runtime/query_worker.py`、Run 事务适配器 | 原租约栅栏下持久化答案及来源、活动时间 |
| `api/query_runs.py` | 旧接口兼容、已删除会话访问检查、安全阶段输出 |
| `api/static/` | 会话列表、消息渲染、滚动、输入、来源、工具入口与连接生命周期 |

前端状态与渲染/连接逻辑应按职责拆成小文件，继续同源静态部署；静态资源白名单随明确新增的文件更新，不开放任意目录或源码读取。保留可独立测试的纯函数边界，避免将所有会话逻辑继续堆入单一 `app.js`。

发布前备份并排空活动 Query Run，再执行增量迁移，协调部署 API、Query Worker 和静态文件，核对相同运行时配置。添加实际阶段事件会影响查询实现指纹，新实验使用新指纹，旧实验和冻结结果保持不变。不在设计阶段迁移、重启或重跑付费评测。

新应用需要对应数据库 schema；启动/就绪检查应识别缺失迁移并给出可操作错误，不能等到第一条问题才发现缺列。回滚应用时保留新增表和可空列，不自动执行破坏性的 downgrade 或清理会话记录。

## 9. 验收标准

### 用户流程

1. 同一会话连续至少 3 轮，全部问题与最终回答按序保留，前后追问使用同一 thread。
2. 刷新、关闭后重新打开，能通过服务端列表找回会话；刷新活动会话只恢复观察，不新增 Run。
3. 两个会话切换、后台完成、旧请求晚返回时，正文、阶段、来源都不串线。
4. 重命名和删除刷新后仍生效；文档与按用户存储的 Mem0 不被删除或清空。
5. 正常 Chat、Fast RAG、Research、澄清、拒答、取消、失败都有正确且简短的展示；未完成时不出现正文草稿。
6. 多轮来源逐条展开正确；历史文档更新、删除与快照缺失行为符合第 7 节。
7. 长历史上翻加载不跳动，主动翻阅不被新消息拉回；输入法 Enter 不误发送；窄屏与键盘操作可用。
8. 聊天页没有事件时间线、检索日志和技术错误原文，工具入口仍能上传文档和管理当前用户记忆。

### 一致性与安全

1. 重复 POST、响应丢失、双击发送和同请求并发只产生一个 Run/Outbox；相同请求 ID 不同问题拒绝。
2. 新建会话未知响应可用原请求 ID 恢复；删除后的创建请求不会重新创建或复活。
3. 多标签页同时发问符合单活动 Run 约束；删除/发问竞争按事务顺序收敛。
4. 用户 A 不能通过 session、Run、游标或来源 ID 读取/修改用户 B 的数据；删除后的旧 Run URL 不绕过会话删除。
5. 公开正文必须走 PublicAnswer；未知事件、脚本样式文本、损坏来源与未审核草稿不能变成 HTML 或正文。
6. 只持久化当前轮真正引用且来源一致的证据；来源和答案的提交遵守现有租约代次检查。
7. 旧查询 API、现有评测 API、配置指纹、取消与审核契约回归通过。

### 验证层次

- 单元测试：去重/标题/阶段映射、来源投影和限制、视图代次、滚动跟随、终态优先和公开字段。
- MySQL 集成：唯一键、行锁、删除竞争、Run/Outbox 原子性、终态来源写入和分页；不能用只含 Fake Repository 的测试代替数据库竞争验证。
- API 集成：用户隔离、分页、幂等、历史恢复、删除访问边界、SSE/状态回退以及旧调用兼容。
- 前端流程：沿用并更新现有 console 测试，覆盖多 session、断线、晚响应、输入法、停止和来源；旧单 answer/timeline DOM 断言应改成新交互契约，不能保留空日志面板只为通过旧测试。
- 浏览器验收：宽屏/窄屏真实滚动与键盘交互、工具抽屉、至少 3 轮对话和刷新活动任务。模型调用可由受控测试依赖驱动；真实 provider 验收使用隔离资源与明确测试配置，单独记录执行结果。

本功能完成不等于整体 RAG 质量或生产发布门禁通过。对话语义超出历史窗口、Worker 崩溃恢复、真实负载与模型质量的既有边界继续单独记录。
