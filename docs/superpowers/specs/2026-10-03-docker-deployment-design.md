# AgenticRAG 应用容器化与安全回滚设计

本设计面向本地开发和单机服务器部署。采用 Docker Compose 管理应用与基础设施，先完成主检索和 Mem0 的统一 ES 认证，再验证完整容器环境。所有实现与测试必须和当前运行环境隔离；测试失败不能要求用户重建当前项目或恢复已被测试修改的业务数据。

本次交付止于独立环境中的可启动、可验证、可回退的容器化方案。不自动替换现有业务服务，不迁移真实数据，不合并或推送实现分支。正式切换是后续单独授权的操作。

设计已于 2026 年 10 月 3 日获用户确认，现进入实现计划审核阶段；目前没有开始容器化代码实现，也没有建立真实业务数据备份。

## 已确认的需求与边界

- 支持本地开发和单机服务器，使用同一套应用镜像和 Compose 定义。
- API、Query Worker、Ingestion Worker 分别运行；两个 Worker 各一个实例。
- 保持 RAG 路由、分块、Embedding 维度、检索排序、记忆策略和当前数据格式不变。
- 现有 ES `9200`、评测 ES `9201`、业务 API、评测 API、共享 MySQL 和 Redis 不停机、不修改配置、不改变认证。
- 容器化验证使用独立 MySQL、Redis、ES、文件存储和测试用户。不能让新 Worker 消费原 Redis Stream。
- 不因测试失败关闭 Mem0、伪造凭证、扩大匿名访问范围或忽略证书错误。
- 用户补充的回滚要求是硬性验收项，而不是文档建议。
- Tool 和 MCP 权限体系仍是原先留待后续处理的事项；本次 ES 连接认证不扩展为该权限体系的重构。

## 当前事实与实验结论

当前代码基线为 `60d543c7c8d181fffce11f8cc5572d5277a0d0fc`。这只是已提交代码的锚点，不代表整个工作区可由一次 Git 操作恢复：当前还有其他任务的评测文档修改、未跟踪评测文档以及 `tmp/`，必须原样保留。

2026 年 10 月 3 日完成的实验结果如下：

| 实验 | 已验证的内容 | 未验证的内容 |
| --- | --- | --- |
| 宿主机应用访问 Docker ES `localhost:9201` | ES 8.19.0；真实 Mem0 2.0.12 初始化、按用户读取、真实 Embedding 后搜索成功 | 容器间认证、记忆写入、完整应用启动 |
| 同一项目配置仅将地址换为 `http://elasticsearch:9200` | 当前无凭证配置在连接前被项目配置工厂拒绝 | 并非一次容器内网络连接实验 |
| 同一项目配置换为 `http://host.docker.internal:9201` | 同样被配置工厂拒绝 | 不证明 Docker 网络不通 |

第一次实验关闭了测试进程的遥测和自动建索引，使用临时 SQLite，并在客户端拒绝 ES 写请求。评测实例中的索引和文档数量未变。不能把这个只读结果表述为整体应用容器化已通过。

代码根因已经明确：`memory/factory.py` 只允许 loopback 地址免认证；已安装 Mem0 的普通 host ES 适配器支持 `basic_auth`，但不会转发其 API key 配置；`bootstrap.py` 的主 ES 客户端目前只接收 URL。

## 部署选择

采用独立的全栈 Compose 作为正式交付形式。仅将应用容器化并复用宿主机数据库，可减少首次数据搬迁，但仍需处理非 loopback 地址和认证，而且不满足本次完整隔离验证的目标，因此不作为默认测试方式。将所有进程塞入单容器不采用，避免生命周期、日志和数据卷职责混在一起。

容器化不等于数据迁移。端口仍为 `9200` 或 `3306`，不能说明新实例持有原数据。首次把真实数据转入新实例需要独立恢复流程；后续在兼容版本下重建容器并复用持久化数据卷，不应反复导入数据。

## 服务与启动顺序

| 服务 | 职责 | 启动前提 |
| --- | --- | --- |
| mysql | 文档、Parent Chunk、运行状态、Outbox、记忆删除标记 | 自身健康检查 |
| redis | 独立任务队列与恢复状态，启用 AOF | 自身健康检查 |
| elasticsearch | Child Chunk 检索及 Mem0 存储，安装 IK | 带认证的集群健康检查 |
| model-init | 将指定版本模型预热到共享模型缓存 | 缓存目录可写；首次下载源可达 |
| app-init | 初始化新库、数据库迁移、索引及别名校验 | 数据库健康；具有初始化权限 |
| api | Web 页面与 API | app-init 成功，依赖可用 |
| query-worker | 查询、重排与记忆处理 | app-init 和 model-init 成功 |
| ingestion-worker | 文档解析、OCR、分块与入库 | app-init 和 model-init 成功 |

API 与两个 Worker 使用同一应用镜像、不同入口命令。基础设施是独立服务，不在应用容器中启动数据库子进程。使用 `service_healthy` 和 `service_completed_successfully` 表达依赖，不用固定 sleep 推测就绪。

容器内 API 绑定 `0.0.0.0:8000`；宿主机默认只绑定 loopback。隔离验证使用空闲的独立宿主端口，不能抢占 `8000`、`8001`、`9200`、`9201`、`3306`、`6379`。基础设施默认不发布宿主端口；诊断需要时仅发布临时 loopback 端口。

容器内部使用服务 DNS：`mysql:3306`、`redis:6379`、`elasticsearch:9200`。不依赖 host networking、宿主机 hosts 修改或将容器服务名伪装成本机地址。

## ES 统一认证

主检索、Mem0、初始化以及本次支持的备份和管理入口使用同一个连接配置解析器。主路径为用户名与密码认证，凭证由运行时 Secret 文件注入，不放在 URL、镜像、Git、日志或评测快照中。

配置设计如下：

- 增加通用 ES 用户、密码、CA 路径和证书校验配置，统一生成同步、异步和 Mem0 客户端参数。
- 旧 `mem0_elasticsearch_*` 配置保留明确的兼容处理；新旧配置同时给出而不一致时拒绝启动，不静默选取其中一套。
- 未配置凭证的现有 loopback 开发连接继续兼容，保证当前宿主机流程不因新增配置而改变。
- Compose 环境必须提供真实用户名密码。普通 host 模式下不能把未被 Mem0 转发的 API key 当成有效认证；该配置应给出明确错误。
- 用户名或密码只提供一个、空 Secret、Secret 文件缺失或不可读，均应在启动前报错。
- 密码中的特殊字符按原值传递，不依赖拼接 URL 或 Shell 转义。Secret 文件只处理约定的末尾换行，不任意裁剪密码内容。
- 主客户端认证失败应可观察；Mem0 降级不能被整体健康检查隐藏。配置成功不等于网络、权限或查询成功。

ES 容器启用安全认证和 HTTPS，生成包含服务名的证书；应用挂载可信 CA，保持证书验证开启。ES 和 MySQL 默认只在项目网络内可达。服务器公网入口的反向代理、HTTPS 和应用用户认证不由 ES 账号替代，不能把当前默认用户模式直接当作公网多用户系统发布。

初始化账号和应用账号分离。初始化账号完成角色、用户、索引与别名初始化；运行中的应用不使用 `elastic` 超级用户。权限仅覆盖本项目知识库索引、别名、Mem0 collection 及必要的 Mem0 附属索引。Docker 环境关闭 Mem0 遥测，不要求运行账号写遥测索引。角色权限以真实操作和越权反向测试验收，不能为了通过测试授予全索引权限。

## 镜像和模型

- 应用使用 Python 3.11 的 Linux CPU 镜像。解析并提交 Linux 可复现依赖锁，不直接将宿主机 Conda 包目录复制进镜像。
- Mem0 保持 `2.0.12`；ES 和 IK 均保持 `8.19.0`。IK 在镜像构建阶段安装并校验下载文件，不在每次启动时下载插件。
- MySQL 和 Redis 以当前 `9.4.0`、`7.4.9` 为兼容基线。镜像版本和目标架构必须在实现时验证并锁定 digest；不可静默降级为其他主版本，也不使用浮动 `latest`。
- 镜像依赖、模型 revision、插件版本和 digest 写入构建记录。宿主机已安装版本只是输入，不是 Linux 镜像已经通过的证据。
- 预热 Qwen tokenizer、BGE reranker 和 Docling 所需模型。模型缓存使用独立持久化卷，运行时检查本地资源完整性，不把下载过程藏在首个用户请求里。
- 明确固定并验证 OCR 后端，避免 macOS 与 Linux 的自动选择改变行为。不增加新切块算法、图片向量化或新的图片描述模型。
- 支持 Linux arm64 和 amd64 构建；分别记录构建及运行验证结果，不能将单架构成功报告为双架构已通过。
- `.dockerignore` 排除 `.git`、环境文件、Secret、`var/`、`tmp/`、备份、测试产物和本地虚拟环境。运行时仅挂载所需资源，不把整个仓库或整个宿主机 `var/` 带进部署镜像。

## 数据与文件隔离

| 状态 | 容器持久化位置与约束 |
| --- | --- |
| MySQL | 独立命名卷，不连接当前业务或评测数据库 |
| Redis | 独立实例与 AOF 卷；即使 Stream 名相同也不能共享原实例 |
| ES | 独立命名卷；知识库与 Mem0 使用明确、受权限约束的索引名 |
| 文档 artifacts | API 与 Worker 共享项目专用目录，统一 UID 与权限 |
| Query 与 Ingestion checkpoint | 挂载所在目录，保留 SQLite WAL/SHM，不只挂载单个文件 |
| Mem0 history | 项目专用 SQLite 目录，不挂载宿主机现有 history |
| Tool invocation 状态 | 独立 SQLite 目录，不能沿用评测或业务文件 |
| 模型缓存 | 独立持久化缓存，与业务状态分离 |

应用以固定非 root 用户运行。初始化过程负责卷目录所有权；禁止以 `chmod 777` 规避权限问题。API 也会访问和初始化 artifacts/checkpoint，不能未经验证将其所需状态卷设为只读。所有本次容器使用的可写路径必须归属于本次 Compose 项目。

## 初始化与重启语义

新安装只初始化本次独立空库，执行 Alembic 和索引初始化；重复启动应幂等，不能删除后重建已有索引或清空记忆。知识库默认使用当前 `index-v4` 和 IK 配置，Embedding 保持 1024 维。

恢复已有数据与新安装是不同流程。恢复流程必须在业务客户端启动及自动创建索引之前校验目标、恢复数据；发现预期索引或 history 缺失应失败，不能通过创建空存储让健康检查变绿。真实数据恢复不在本次自动执行范围内。

Worker 必须在模型加载和依赖初始化完成后报告就绪，并有独立可检查的心跳。容器入口使用直接执行 Python 的形式，保证终止信号能送到业务进程。停止时先停止领取新任务，再等待当前任务的有界收尾；超时中断的任务依靠现有 PEL、checkpoint 和幂等机制恢复，不能假设 API 健康就代表 Worker 健康。不能把 Query 单次 300 秒预算当成整批任务或 OCR 的完整退出上界。

## 测试失败时的回滚

### 实施前建立基线

实现开始前，在独立 worktree 和 `codex/` 实现分支工作，不在共享 main 上覆盖其他任务的改动。记录当时的源提交、工作区状态、现有容器和卷的身份、端口、当前配置文件的哈希及服务启动方式；记录中不包含凭证明文。当前已有未提交和未跟踪文件不是可丢弃内容。

基线记录是核对依据，不冒充数据库一致性备份。完整数据备份只在未来确实要切换或迁移之前执行；本次隔离测试不写现有数据库，因此不能为了“准备回滚”对现有实例实施不必要的停机或搬迁。

### 隔离测试失败

1. 停止本次 Compose 项目接收请求和任务。
2. 核对项目名、标签及容器身份，只停止本次创建的容器和网络，不执行全局 Docker 清理。
3. 默认保留失败环境的数据卷、日志、构建信息和测试报告，供定位问题；删除测试数据必须按已核实的具体目标操作，不默认执行 `down -v`。
4. 当前业务代码、环境文件、数据库和服务未切换，因此继续保持原运行方式，无需对它们执行数据恢复。
5. 未合并的实现保留在隔离 worktree；需要撤回时只处理本次分支和产物，不使用 `reset --hard` 或覆盖共享 main 的脏文件。
6. 对照基线验证原业务及评测服务仍可访问，确认未改动原配置和现有挂载；记录回滚演练结果。

共享宿主机仍可能出现 CPU、内存或磁盘争用，所以启动测试栈前检查资源并设置限额；资源不足时停止扩展测试，不通过关闭现有服务腾出资源。隔离不等于可以保证宿主机没有任何运行风险。

### 未来正式切换

正式切换需用户另行授权，并先完成停写、队列排空或一致性捕获、可验证备份和恢复演练。备份范围包括 MySQL、Redis、ES 的全部必要索引、artifacts、两个 checkpoint、Mem0 history 和 Tool invocation 状态。

新环境未产生业务写入时，可按已验证的切换记录恢复旧入口和旧服务。新环境一旦产生写入，不能直接切回旧库并声称无数据损失；必须先停止新写入、保存新增状态并执行经过验证的数据回迁或前向修复方案。不得允许新旧 Worker 同时消费同一业务队列或同时操作同一 SQLite 状态。

## 验收门槛

以下测试必须由实际应用镜像在实际容器网络内执行，不能用宿主机客户端测试或配置字典检查替代。写入测试仅使用独立数据和测试用户，真实模型调用只发送合成测试内容。

| 门槛 | 必须观察到的证据 |
| --- | --- |
| 网络与 TLS | 服务名解析正确；使用可信 CA 连接成功；错误 CA 被拒绝 |
| 认证 | 两种 ES 客户端使用正确账号成功；错误密码和缺失凭证均被拒绝 |
| 权限 | 项目范围内操作成功；尝试访问无关索引被拒绝；运行账号不是超级用户 |
| Mem0 | 初始化、新增、按用户读取、真实 Embedding 检索、删除成功；不同用户不能读取测试记忆 |
| 知识库 | IK 分析器、中文 BM25、英文查询及向量检索成功，只有既定词法检索通道 |
| 完整应用 | API 与两个 Worker 正常；Mem0 未降级；文本 PDF、扫描 PDF、XLSX 上传并完成问答 |
| 持久化 | 重启及重建容器并保留卷后，测试文档和记忆仍可访问 |
| 队列恢复 | 带未完成任务停止并重启，任务可恢复且没有重复业务效果 |
| 幂等初始化 | 重复启动不重置数据；恢复模式的缺失数据不能被自动创建掩盖 |
| 配置兼容 | 原 loopback 无认证模式回归通过；新旧配置冲突明确报错；日志无 Secret |
| 回滚 | 故意让隔离栈认证测试失败后停止该栈，现有环境保持可用，代码和配置未被覆盖 |

仅空索引搜索返回 200 不满足 Mem0 写入和召回验收。构建成功不代表模型预热、OCR 或应用启动成功。任何门槛未满足，都不合并、切换或迁移现有业务环境。

## 交付顺序和代码边界

第一阶段统一 ES 连接与认证配置，覆盖主应用、Mem0、初始化和关联管理入口，并增加配置及真实认证测试。第二阶段构建带依赖锁和模型缓存的应用镜像以及 ES IK 镜像。第三阶段接入 Compose、初始化、健康检查、停止恢复和状态卷。最后执行完整隔离验收与回滚演练，交付使用文档和测试报告。

预期变更范围包括 `src/agentic_rag/config.py`、统一 ES 客户端工厂、`bootstrap.py`、`memory/factory.py`、相关管理脚本、Worker 生命周期、Dockerfile、Compose、Secret 示例、依赖锁、模型预热与容器验证脚本，以及对应测试和部署文档。具体文件接口与逐步测试命令由书面设计确认后的实现计划确定。

不顺带修改真实数据迁移工具的业务语义。现有备份与恢复脚本不能未经审计直接充当全栈迁移工具：此前检查已发现单个 ES generation 备份、Mem0 和 Tool 状态遗漏、空目标约束以及 Redis namespace 不匹配等边界，未来迁移阶段必须单独处理。现有恢复流程会升级 MySQL 到执行代码的 Alembic head，因此也不能直接作为恢复到任意历史版本的工具。
